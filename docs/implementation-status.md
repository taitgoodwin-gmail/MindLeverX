### Classification rules

- **Full:** all currently specified applicable behavior has concrete implementation evidence. Negative capability requirements may be Full through an enforced prohibition; absent positive journeys are not Full. Conditional behavior is identified explicitly. Full does not mean tested, production-ready, approved or accepted.
- **Partial:** concrete implementation covers some behavior, with at least one named missing element. Nearby scaffolding alone does not earn Partial if it implements none of the required domain behavior.
- **None:** inspected code/schema/routes do not implement the required behavior. For evaluation/process proposals, planning documents alone do not count as coded measurement/evaluation. Evidence links identify the inspected boundary, not a positive implementation.
- **Unknown:** available material cannot support a classification, with a specific reason. All 105 checkout rows were inspected, so the current table has zero Unknown; unseen Mac work is outside this denominator.
- **Executable test coverage:** Present means the whole specified behavior has checked-in executable coverage; Partial means bounded sub-behavior tests exist; Absent means none found for the required behavior. Canonical scenario prose is not executable coverage.
- **Acceptance execution:** PASS/FAIL/BLOCKED/NOT RUN/Unknown describes the canonical requirement acceptance boundary only. Existing component tests can pass while this remains NOT RUN.
